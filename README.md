# Reminderly — сервис напоминаний (ПР11: Django Forms и изображения)

Python 3.11+ / Django 5.2. Существующий проект ПР1–ПР7 продолжен:
веб-интерфейс, CRUD, поиск и статистика используют **Django ORM**.
Основная база — **`db.sqlite3`** из `reminder_site/settings.py`.
Локальная `data/reminderly.sqlite` служит источником переноса ПР7.
SQLite-базы, резервные копии и секреты исключены из Git; новую ORM-базу
создают миграции. Для существующей базы сначала сделайте резервную копию
по инструкции ниже.

## Формы и изображения ПР11

Создание и редактирование пяти сущностей выполняется через `ModelForm`;
фильтры задач и напоминаний — через GET-формы с сохранением введённых
значений и показом ошибок. POST-формы защищены CSRF. Напоминания проверяют
прошедшую дату, дубликат текста/категории/пользователя/времени и согласованность
связей. При редактировании текущая запись исключается из проверки дубликатов,
а неизменённая историческая дата допустима. Отменённые и завершённые задачи
не блокируют повторное напоминание. Отмена активной задачи выполняется только
POST-запросом, сохраняет запись и связи; GET возвращает 405.

У категории необязательное поле `image`. Для обработки нужен Pillow из
`requirements.txt`. Пользовательская форма и существующий `CategoryAdmin`
поддерживают загрузку, замену и очистку изображения. Сервер проверяет
содержимое файла: JPEG, PNG или WebP, не более **5 × 1024 × 1024 байт**.
Расширение и MIME сами по себе не подтверждают допустимость файла.
Ошибочный файл не сохраняется; при редактировании прежнее изображение остаётся.

Файлы сохраняются в `MEDIA_ROOT = BASE_DIR / 'media'`, подкаталог `categories/`,
URL начинается с `/media/`. Django раздаёт их только при `DEBUG=True`.
Список и страница категории показывают изображение либо сообщение об отсутствии.
`media/`, базы, резервные копии и `.env` исключены из Git.
При замене/очистке Django сохраняет прежний файл на диске: автоматическое
удаление не настроено. Для рабочего развёртывания медиа раздаёт веб-сервер.

Ручная демонстрация после запуска:

1. На `/categories/new/` создайте категории с JPEG, PNG, WebP и без изображения;
   проверьте список `/categories/`, карточку и файл в `media/categories/`.
2. В карточке нажмите «Редактировать»: замените файл, сохраните без нового
   файла, затем отметьте очистку. Проверьте каждый результат.
3. Попробуйте текстовый файл с расширением `.png`, GIF и изображение больше
   5 МБ. Должны появиться ошибки; запись и прежнее изображение сохраняются.
4. На `/admin/` создайте категорию с изображением и замените его;
   проверьте результат в пользовательской карточке.
5. На `/reminders/` совместите поиск, категорию, дату, статус и сортировку;
   перейдите на следующую страницу. На `/tasks/` проверьте также пользователя.
   Введите неверную дату — форма должна показать ошибку и сохранить ввод.
6. Создайте корректное напоминание на будущее, повторите его создание,
   попробуйте прошлую дату; ошибочные варианты не сохраняются. При
   редактировании сохраните текущие значения, затем попробуйте конфликт
   с другой активной записью. Несуществующий ID редактирования возвращает 404.
7. Отмените активную задачу из её карточки, проверьте статус и фильтр «В работе».
   Повторите связанное напоминание на то же время: отменённая задача
   не блокирует создание. GET `/tasks/<id>/cancel/` возвращает 405.
8. Проверьте сценарии ПР10: Admin CRUD, поиск, фильтры, inline, действия
   над статусами, автодополнение, статистику, slug и прежние URL по ID.

Перед применением `planner.0006_category_image` 19.11.2026 сохранена копия
`backups/db-before-pr11-20261119-202915.sqlite3`; `PRAGMA integrity_check` — `ok`.
Копия локальная, в Git не включается.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

На новой установке база будет пустой. Необязательно: загрузите демонстрационные
данные из отслеживаемых JSON (только если исходная база ПР7 ещё не создана):

```bash
python -m db.import_json
python manage.py import_pr7
```

Для переноса существующих пользовательских данных ПР7 выполняйте только
`python manage.py import_pr7`, сохранив локальную `data/reminderly.sqlite`.
Повторный `db.import_json` заменяет её содержимое данными JSON.

Windows PowerShell: создайте окружение через `py -m venv .venv`,
активируйте `.venv\Scripts\Activate.ps1`, затем выполните команды `python` выше.
Открыть <http://127.0.0.1:8000/>. Bootstrap подключается через CDN,
собственные CSS, JS и логотип — локально.

`python main.py` запускает прежнюю консольную программу, которая продолжает
работать с JSON. Классы из каталога `models/` не являются Django-моделями.

## Административная панель (сохранена из ПР10)

После применения миграций создайте учётную запись Django Auth:

Откройте <http://127.0.0.1:8000/admin/> и войдите с созданной учётной записью.
Пароль вводится интерактивно; не сохраняйте его в коде или репозитории.
`planner.User` — пользователь сервиса, он не предоставляет доступ в Admin.
Для входа нужны активная учётная запись Django Auth и признак `is_staff`;
права на модели назначаются отдельно (суперпользователь имеет все права).

В Admin доступны все пять моделей: поиск (включая связанные поля), фильтры,

только для чтения. Проверки совместимости связей находятся в `model.clean()`
и используются как Admin (включая inline), так и обычными веб-формами.
Миграция `0005_admin_localization` сохраняет русские названия моделей и полей.

## Модели и миграции

Пять моделей находятся в `planner/models.py`. Django создаёт отдельные таблицы
`planner_user`, `planner_category`, `planner_time`, `planner_task`,
`planner_reminder`. Поля соответствуют исторической `sql/schema.sql`:

| Модель | Поля и связи |
| --- | --- |
| `User` | `id`, `name`, уникальный `email` (`EmailField`) |
| `Category` | `id`, уникальные `name` и `slug`, `description` (`TextField`, по умолчанию пустая строка), необязательное `image` (`ImageField`) |
| `Time` | `id`, `label`, `moment` (`DateTimeField`) |
| `Task` | `id`, `title`, `description`, обязательные `user`, `category`, `status` (`TextChoices`), `is_completed` (хранимый `GeneratedField`) |
| `Reminder` | `id`, `text`, обязательная `category`, `remind_at` (`DateTimeField`, индекс), необязательные `user`, `task`, `time` |

`planner.User` — предметный пользователь сервиса, отдельный от `auth.User`.
Первичные ключи создаёт Django (`BigAutoField`). Все внешние ключи используют
`on_delete=PROTECT`; обратные связи доступны через `.tasks` и `.reminders`.
Необязательные связи напоминания имеют `null=True, blank=True`.
Уникальность email и названия категории обеспечивается БД; FK индексируются.

Начальная миграция: `planner/migrations/0001_initial.py`.

```bash
python manage.py makemigrations planner  # после изменения моделей
python manage.py migrate
python manage.py showmigrations
python manage.py makemigrations --check --dry-run
```

## Перенос данных ПР7

```bash
python manage.py import_pr7
# Другой источник:
python manage.py import_pr7 --source /absolute/path/reminderly.sqlite
```

Команда `planner/management/commands/import_pr7.py` читает исходную SQLite
в режиме **только чтения** (`mode=ro`) и в согласованном снимке.
Запись выполняется ORM внутри единой `transaction.atomic()` в порядке:
пользователи → категории → время → задачи → напоминания.
Сохраняются все ID, поля, внешние ключи и необязательные значения NULL.
JSON при переносе не используется: изменения пользователя в SQLite ПР7
попадают в новую БД.

При повторном запуске полностью совпадающие записи пропускаются.
Если существующий ID имеет другие значения либо нарушено уникальное
ограничение/FK, команда сообщает об ошибке и откатывает весь перенос,
включая уже добавленные строки. Никакие существующие записи не обновляются
и не удаляются. Конфликт нужно разрешить явно перед повторным переносом.
Записи, созданные в ORM и отсутствующие в источнике, сохраняются.

`USE_TZ=True`, `TIME_ZONE=Europe/Moscow`: прежние даты без часового пояса
интерпретируются в этой зоне; Django сохраняет моменты в UTC и показывает
в местном времени. Сравнение при повторном переносе выполняется по значениям
datetime, поэтому смена формата хранения не создаёт ложного конфликта.

Результат первоначального переноса текущей базы:

| Сущность | Источник ПР7 | ORM |
| --- | ---: | ---: |
| Пользователи | 2 | 2 |
| Категории | 3 | 3 |
| Время | 2 | 2 |
| Задачи | 3 | 3 |
| Напоминания | 3 | 3 |

Всего 13 записей; повторный запуск не создаёт новых строк.

## Страницы и CRUD

| URL | Возможности |
| --- | --- |
| `/` | Счётчики всех пяти сущностей |
| `/reminders/` | Поиск по тексту, категория, дата включительно, статус, сортировка и страницы |
| `/search/` | Сохранённый адрес того же поиска; форма отправляет GET на `/reminders/` |
| `/tasks/` | Поиск по названию/описанию, категория, `status=open` / `done` / `cancelled`, пользователь и дата напоминания |
| `/users/` | Поиск по имени/email |
| `/categories/` | Поиск по названию/описанию |
| `/times/` | Поиск по названию, фильтр даты `day=YYYY-MM-DD` |
| `/statistics/?min_tasks=2` | Итоги, группы по категориям/пользователям, порог числа задач |

Для каждого из пяти разделов сохранены `/<раздел>/<id>/`,
`/<раздел>/new/`, `/<раздел>/<id>/edit/`, `/<раздел>/<id>/delete/`.
Формы остаются обычными Django Forms с CSRF; операции выполняются через
`objects.create()`, `save()`, `delete()` и транзакции ORM.
GET удаления показывает подтверждение; изменение данных выполняет POST.

Сохраняется проверка совместимости категории и пользователя выбранной задачи
с напоминанием; связанное время должно совпадать с датой напоминания.
Редактирование задачи/времени не может нарушить существующие связи.
Удаление объекта с зависимостями запрещено (`PROTECT`, HTTP 409).
Отсутствующая запись возвращает 404, ошибки полей/уникальности показываются
в форме, ошибки доступности БД — на странице 500.

На `/reminders/` доступны `sort=date`, `sort=-date`, `sort=category`.
Порядок стабилизирован ID. `Paginator` выводит **по 5 записей** после
поиска, фильтрации и сортировки. Ссылки сохраняют остальные GET-параметры;
новый поиск начинает показ с первой страницы.
Неизвестные сортировки/статусы заменяются значениями по умолчанию,
невалидные ID фильтров игнорируются, ошибочная дата сопровождается сообщением.
Некорректная страница показывает первую, номер вне диапазона — последнюю.

Статус сравнивает моменты с точностью до минуты в текущем часовом поясе:
текущая минута — «актуально», более поздняя — «ещё не наступило»,
более ранняя — «просрочено». Фильтры и карточки используют одинаковое правило.

## Содержательные ORM-запросы ПР9

В `planner/views.py`, `planner/forms.py`, `homepage/views.py` реализованы
более 15 выражений, используемых существующими страницами:

| Группа | Примеры |
| --- | --- |
| Получение списка и записи (2) | `User.objects.all()`, `get_object_or_404(User, pk=...)` (ORM `get`) |
| Фильтрация (4+) | `filter(category__id=...)` по связанному полю; `filter(remind_at__date__lte=...)`; несколько условий `filter(remind_at__gte=..., remind_at__lt=...)`; `filter(moment__date=...)`; `Task.objects.active()` |
| Поиск (2+) | `filter(text__icontains=q)`; `Q(name__icontains=q) \| Q(email__icontains=q)`; аналогичные поиски задач и категорий |
| Сортировка (2+) | `order_by('remind_at', 'id')`, `order_by('category__name', 'remind_at', 'id')`, обратная сортировка даты |
| Связанные объекты (2+) | `Reminder.objects.select_related('category', 'user', 'task', 'time')`; `Task.objects.select_related('user', 'category')`; обратные `.tasks` / `.reminders` |
| Статистика (2+) | `Task.objects.aggregate(Count('id'), Sum(...))`; `Category.objects.annotate(task_count=Count('tasks'), done_count=Sum(...))`; аналогичные группы пользователей и напоминаний |
| Пагинация (1) | `Paginator(отсортированный_queryset, 5).get_page(...)` |

Статистика показывает число всех задач, выполненных, активных и отменённых; количество задач/выполненных по категориям и
пользователям; количество напоминаний по категориям; пользователи с числом
задач не ниже `min_tasks` (1–100). Группы без связанных записей включаются
с нулевыми значениями. Для `Sum` вычисляемое булево поле приводится к IntegerField;
пустая сумма равна нулю. Независимые группировки не размножают строки связей.

## Изменения ПР10

`Task.status` использует `Task.Status`: `ACTIVE`, `COMPLETED`, `CANCELLED`.
`is_completed` — хранимый `GeneratedField`, равный `True` только для
`COMPLETED`. Изменять нужно `status`; для получения пересчитанного значения
у уже загруженного объекта вызовите `refresh_from_db()`.

Менеджер `Task.objects` предоставляет цепочки `active()`, `completed()`,
`cancelled()`, `for_date(day)`. Последний метод выбирает задачи по локальной
дате связанных напоминаний без дубликатов. Фильтры списка `open` и `done`
сохранены, добавлен `cancelled`; отменённые задачи не считаются активными.
`import_pr7` преобразует старый bool в статус и сохраняет проверку конфликтов.

У категорий автоматически создаётся уникальный ASCII slug с транслитерацией
кириллицы, обработкой пустого результата, коллизий и зарезервированных URL.
Переименование сохраняет slug. Ссылки и перенаправления CRUD используют
`get_absolute_url()`; прежние адреса `/categories/<id>/` также работают.

Перед применением миграций создайте резервную копию актуальной БД, например:

```bash
mkdir -p backups
python -c "import sqlite3; s = sqlite3.connect('db.sqlite3'); d = sqlite3.connect('backups/before-pr10.sqlite3'); s.backup(d); d.close(); s.close()"
python manage.py migrate
```

Используйте новое имя копии при каждом запуске. Миграция `0002` добавляет поля;
отдельная `0003` переносит `False → ACTIVE`, `True → COMPLETED` и заполняет slug;
`0004` заменяет старый bool вычисляемой колонкой и включает уникальность slug.
Старая `0001` не изменена. При откате к старой схеме отменённые задачи получают
`is_completed=False`, поскольку прежняя схема не хранит третий статус.

## Django Debug Toolbar и фактический SQL-анализ

Установлена `django-debug-toolbar==6.2.0`, совместимая с Django 5.2
(проверено установкой и интеграционными тестами).
[Документация установки](https://django-debug-toolbar.readthedocs.io/en/stable/installation.html).
Приложение, middleware после SecurityMiddleware и URL `/__debug__/`
подключаются только при `DEBUG=True` вне pytest / `manage.py test`.
Стандартная проверка панели дополнительно разрешает только `INTERNAL_IPS`:
`127.0.0.1` и `::1`. Не добавляйте туда внешние адреса.

Локально: `DJANGO_DEBUG=1 python manage.py runserver`, откройте
[список](http://127.0.0.1:8000/reminders/) и вкладку SQL боковой панели.
Проверьте карточку, GET-фильтры и следующую страницу. На Windows PowerShell
задайте `$env:DJANGO_DEBUG="1"` перед запуском сервера.
При `DJANGO_DEBUG=0` приложение, middleware и маршруты панели отсутствуют.
Для сервера разработки используйте стандартную привязку к loopback.

Измерено 19.11.2026 через настоящую SQLPanel Debug Toolbar и Django Client
с локальным IP; отдельная SQLite `:memory:`, все миграции применены,
анонимные GET, наборы из 1, 5 и 12 напоминаний со всеми четырьмя связями.
Создание тестовых данных и миграции в число запросов страницы не входят.

| Сценарий | 1 запись | 5 записей | 12 записей |
| --- | ---: | ---: | ---: |
| `/reminders/` | 4 | 4 | 4 |
| `/reminders/<id>/` | 2 | 2 | 2 |
| Поиск + категория + дата + upcoming + сортировка category | 5 | 5 | 5 |
| `?page=2` | 4 | 4 | 4 |
| Поиск без совпадений | 3 | 3 | 3 |

Назначение каждого запроса непустого списка:

1. `COUNT(*)` отфильтрованного набора — число страниц Paginator.
2. `SELECT` пяти полей через `values()` с JOIN категории и пользователя —
   строки текущей страницы и связанные имена без дополнительных обращений.
   На 12 записях первая страница использует `LIMIT 5`, вторая —
   `LIMIT 5 OFFSET 5`; сортировка стабилизирована ID.
3. Отдельный `COUNT(*)` всех напоминаний — общий счётчик навигации из
   контекстного процессора. При фильтрации он намеренно отличается от
   Paginator.count; без фильтров значения совпадают. Это постоянный запрос
   общего шаблона, возможная дальнейшая оптимизация — переиспользование
   результата на нефильтрованной странице.
4. `SELECT` категорий — варианты фильтра, в том числе без совпадений.

В ПР11 при выбранной категории добавляется один SELECT для проверки
`ModelChoiceField`: 5 запросов независимо от числа строк. Остальные
приведённые значения сохранены из измерений ПР10.

На карточке один SELECT с JOIN category/user/task/time (`select_related`)
и один общий COUNT из контекстного процессора. Пустой список не выполняет
SELECT строк. Необязательные связи используют LEFT OUTER JOIN, обязательная
категория — INNER JOIN. Поиск через Q объединяет текст и связанные имена OR,
остальные фильтры добавляются AND; обе страницы используют одинаковый WHERE.

**N+1 не обнаружено:** число запросов не растёт с числом объектов;
доступ к уже загруженным связям карточки и списков Admin выполняет 0 новых
запросов. Полное SQL-время этих локальных проб: 0,060–0,417 мс суммарно
на страницу; это измерения маленькой in-memory БД, не нагрузочный тест.
Поиск `icontains` и преобразование даты в местный часовой пояс могут требовать
сканирования на больших объёмах; дополнительных индексов без такого профиля
не добавлено. Регрессионная проверка: `python -m pytest tests/test_debug_toolbar.py -v`.

## Структура и историческая реализация

- `planner/models.py`, `migrations/` — ORM-схема и миграция.
- `planner/management/commands/import_pr7.py` — перенос из SQLite ПР7.
- `planner/views.py`, `crud_views.py`, `forms.py` — веб-интерфейс через ORM.
- `planner/templates/planner/` — прежние шаблоны; добавлены сортировка и пагинация.
- `homepage/`, `templates/` — главная, статические ресурсы, общие шаблоны и ошибки.
- `db.sqlite3` — основная Django ORM-база и служебные таблицы Django.
- `data/reminderly.sqlite` — сохранённая исходная БД ПР7; `data/*.json` — консольные данные.
- `db/`, `sql/` — исторический SQL-слой ПР7, веб-интерфейс его больше не импортирует.
- `models/`, `main.py`, `reminders.py`, `storage.py`, `project_data.py` — прежняя консольная/JSON-реализация.
- `tests/` — исторические SQL/консольные тесты, адаптированные веб-тесты и тесты ПР9.

Исторические `python -m db.init_db` и `python -m db.import_json` не нужны
для обычного запуска сайта. Второй используется для первоначальных демоданных
и заменяет данные исходной БД значениями JSON;
не запускайте его для переноса пользовательских изменений ПР7.
Веб-CRUD сохраняет изменения только в `db.sqlite3`.

## Проверка

```bash
python manage.py check
python manage.py showmigrations
python manage.py makemigrations --check --dry-run
python -m pytest -v
python -m flake8 .
```

Веб-тесты используют отдельную временную Django test DB, миграции и
откатываемые транзакции; рабочие SQLite-файлы не изменяются.
Дополнительный pytest-плагин не требуется. Тестовые данные загружаются
из отдельной копии исторической JSON-фикстуры через команду переноса.
SQL-тесты ПР7 сохранены и работают со своими временными SQLite-файлами.
Тесты ПР9 проверяют значения и ID при переносе, повторный запуск,
откат при конфликтах, защиту связей, пагинацию, сортировку,
параметры GET, локальные даты/статусы и статистику с пустыми группами.

Результат проверки 19.11.2026 (Python 3.13.3, Django 5.2.18,
django-debug-toolbar 6.2.0, Pillow 12.3.0): **295 тестов пройдено**, пропусков
и ошибок нет. `migrate` выполнен; `check`: 0 проблем;
`showmigrations`: все 24 миграции применены, включая
`planner.0001`–`0006`; `makemigrations --check --dry-run`: No changes detected;
flake8: код завершения 0, замечаний нет.

Проверены права и CRUD Admin, поиск/фильтры/inline/autocomplete/действия,
перенос старых bool-статусов и связей с откатом миграций, GeneratedField после
`save()` и `update()`, цепочки QuerySet, slug и прежние ID URL, общий контекст,
исторические консольные/SQL-сценарии, веб-CRUD, CSRF, ошибки и статистика.
