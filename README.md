# Reminderly — сервис напоминаний (ПР9: Django ORM)

Python 3.11+ / Django 5.2. Существующий проект ПР1–ПР7 продолжен:
веб-интерфейс, CRUD, поиск и статистика используют **Django ORM**.
Основная база — **`db.sqlite3`** из `reminder_site/settings.py`.
Исходная `data/reminderly.sqlite` сохранена как база ПР7 и источник переноса.
Обе SQLite-базы включены в репозиторий; миграции и команда переноса позволяют
подготовить новую ORM-базу самостоятельно.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

Windows PowerShell: создайте окружение через `py -m venv .venv`,
активируйте `.venv\Scripts\Activate.ps1`, затем выполните команды `python` выше.
Открыть <http://127.0.0.1:8000/>. Bootstrap подключается через CDN,
собственные CSS, JS и логотип — локально.

`python main.py` запускает прежнюю консольную программу, которая продолжает
работать с JSON. Классы из каталога `models/` не являются Django-моделями.

## Модели и миграции

Пять моделей находятся в `planner/models.py`. Django создаёт отдельные таблицы
`planner_user`, `planner_category`, `planner_time`, `planner_task`,
`planner_reminder`. Поля соответствуют исторической `sql/schema.sql`:

| Модель | Поля и связи |
| --- | --- |
| `User` | `id`, `name`, уникальный `email` (`EmailField`) |
| `Category` | `id`, уникальный `name`, `description` (`TextField`, по умолчанию пустая строка) |
| `Time` | `id`, `label`, `moment` (`DateTimeField`) |
| `Task` | `id`, `title`, `description`, обязательные `user`, `category`, `is_completed` (`BooleanField`, False) |
| `Reminder` | `id`, `text`, обязательная `category`, `remind_at` (`DateTimeField`, индекс), необязательные `user`, `task`, `time` |

`planner.User` — предметный пользователь сервиса, отдельный от `auth.User`.
Первичные ключи создаёт Django (`BigAutoField`). Все внешние ключи используют
`on_delete=PROTECT`; обратные связи доступны через `.tasks` и `.reminders`.
Необязательные связи напоминания имеют `null=True, blank=True`.
Уникальность email и названия категории обеспечивается БД; FK индексируются.

Начальная миграция: `planner/migrations/0001_initial.py`.

```bash
python manage.py makemigrations planner  # после изменения моделей
python manage.py migrate
python manage.py showmigrations
python manage.py makemigrations --check --dry-run
```

## Перенос данных ПР7

```bash
python manage.py import_pr7
# Другой источник:
python manage.py import_pr7 --source /absolute/path/reminderly.sqlite
```

Команда `planner/management/commands/import_pr7.py` читает исходную SQLite
в режиме **только чтения** (`mode=ro`) и в согласованном снимке.
Запись выполняется ORM внутри единой `transaction.atomic()` в порядке:
пользователи → категории → время → задачи → напоминания.
Сохраняются все ID, поля, внешние ключи и необязательные значения NULL.
JSON при переносе не используется: изменения пользователя в SQLite ПР7
попадают в новую БД.

При повторном запуске полностью совпадающие записи пропускаются.
Если существующий ID имеет другие значения либо нарушено уникальное
ограничение/FK, команда сообщает об ошибке и откатывает весь перенос,
включая уже добавленные строки. Никакие существующие записи не обновляются
и не удаляются. Конфликт нужно разрешить явно перед повторным переносом.
Записи, созданные в ORM и отсутствующие в источнике, сохраняются.

`USE_TZ=True`, `TIME_ZONE=Europe/Moscow`: прежние даты без часового пояса
интерпретируются в этой зоне; Django сохраняет моменты в UTC и показывает
в местном времени. Сравнение при повторном переносе выполняется по значениям
datetime, поэтому смена формата хранения не создаёт ложного конфликта.

Результат первоначального переноса текущей базы:

| Сущность | Источник ПР7 | ORM |
| --- | ---: | ---: |
| Пользователи | 2 | 2 |
| Категории | 3 | 3 |
| Время | 2 | 2 |
| Задачи | 3 | 3 |
| Напоминания | 3 | 3 |

Всего 13 записей; повторный запуск не создаёт новых строк.

## Страницы и CRUD

| URL | Возможности |
| --- | --- |
| `/` | Счётчики всех пяти сущностей |
| `/reminders/` | Поиск по тексту, категория, дата включительно, статус, сортировка и страницы |
| `/search/` | Сохранённый адрес того же поиска; форма отправляет GET на `/reminders/` |
| `/tasks/` | Поиск по названию/описанию, категория, `status=open` / `done` |
| `/users/` | Поиск по имени/email |
| `/categories/` | Поиск по названию/описанию |
| `/times/` | Поиск по названию, фильтр даты `day=YYYY-MM-DD` |
| `/statistics/?min_tasks=2` | Итоги, группы по категориям/пользователям, порог числа задач |

Для каждого из пяти разделов сохранены `/<раздел>/<id>/`,
`/<раздел>/new/`, `/<раздел>/<id>/edit/`, `/<раздел>/<id>/delete/`.
Формы остаются обычными Django Forms с CSRF; операции выполняются через
`objects.create()`, `save()`, `delete()` и транзакции ORM.
GET удаления показывает подтверждение; изменение данных выполняет POST.

Сохраняется проверка совместимости категории и пользователя выбранной задачи
с напоминанием; связанное время должно совпадать с датой напоминания.
Редактирование задачи/времени не может нарушить существующие связи.
Удаление объекта с зависимостями запрещено (`PROTECT`, HTTP 409).
Отсутствующая запись возвращает 404, ошибки полей/уникальности показываются
в форме, ошибки доступности БД — на странице 500.

На `/reminders/` доступны `sort=date`, `sort=-date`, `sort=category`.
Порядок стабилизирован ID. `Paginator` выводит **по 5 записей** после
поиска, фильтрации и сортировки. Ссылки сохраняют остальные GET-параметры;
новый поиск начинает показ с первой страницы.
Неизвестные сортировки/статусы заменяются значениями по умолчанию,
невалидные ID фильтров игнорируются, ошибочная дата сопровождается сообщением.
Некорректная страница показывает первую, номер вне диапазона — последнюю.

Статус сравнивает моменты с точностью до минуты в текущем часовом поясе:
текущая минута — «актуально», более поздняя — «ещё не наступило»,
более ранняя — «просрочено». Фильтры и карточки используют одинаковое правило.

## Содержательные ORM-запросы ПР9

В `planner/views.py`, `planner/forms.py`, `homepage/views.py` реализованы
более 15 выражений, используемых существующими страницами:

| Группа | Примеры |
| --- | --- |
| Получение списка и записи (2) | `User.objects.all()`, `get_object_or_404(User, pk=...)` (ORM `get`) |
| Фильтрация (4+) | `filter(category__id=...)` по связанному полю; `filter(remind_at__date__lte=...)`; несколько условий `filter(remind_at__gte=..., remind_at__lt=...)`; `filter(moment__date=...)`; `exclude(is_completed=True)` |
| Поиск (2+) | `filter(text__icontains=q)`; `Q(name__icontains=q) \| Q(email__icontains=q)`; аналогичные поиски задач и категорий |
| Сортировка (2+) | `order_by('remind_at', 'id')`, `order_by('category__name', 'remind_at', 'id')`, обратная сортировка даты |
| Связанные объекты (2+) | `Reminder.objects.select_related('category', 'user', 'task', 'time')`; `Task.objects.select_related('user', 'category')`; обратные `.tasks` / `.reminders` |
| Статистика (2+) | `Task.objects.aggregate(Count('id'), Sum(...))`; `Category.objects.annotate(task_count=Count('tasks'), done_count=Sum(...))`; аналогичные группы пользователей и напоминаний |
| Пагинация (1) | `Paginator(отсортированный_queryset, 5).get_page(...)` |

Правила статистики сохранены: число всех задач, сумма выполненных,
разность для открытых; количество задач/выполненных по категориям и
пользователям; количество напоминаний по категориям; пользователи с числом
задач не ниже `min_tasks` (1–100). Группы без связанных записей включаются
с нулевыми значениями. Для `Sum` BooleanField приводится к IntegerField;
пустая сумма равна нулю. Независимые группировки не размножают строки связей.

## Структура и историческая реализация

- `planner/models.py`, `migrations/` — ORM-схема и миграция.
- `planner/management/commands/import_pr7.py` — перенос из SQLite ПР7.
- `planner/views.py`, `crud_views.py`, `forms.py` — веб-интерфейс через ORM.
- `planner/templates/planner/` — прежние шаблоны; добавлены сортировка и пагинация.
- `homepage/`, `templates/` — главная, статические ресурсы, общие шаблоны и ошибки.
- `db.sqlite3` — основная Django ORM-база и служебные таблицы Django.
- `data/reminderly.sqlite` — сохранённая исходная БД ПР7; `data/*.json` — консольные данные.
- `db/`, `sql/` — исторический SQL-слой ПР7, веб-интерфейс его больше не импортирует.
- `models/`, `main.py`, `reminders.py`, `storage.py`, `project_data.py` — прежняя консольная/JSON-реализация.
- `tests/` — исторические SQL/консольные тесты, адаптированные веб-тесты и тесты ПР9.

Исторические `python -m db.init_db` и `python -m db.import_json` не нужны
для запуска сайта. Второй заменяет данные исходной БД значениями JSON;
не запускайте его для переноса пользовательских изменений ПР7.
Веб-CRUD сохраняет изменения только в `db.sqlite3`.

## Проверка

```bash
python manage.py check
python manage.py showmigrations
python manage.py makemigrations --check --dry-run
python -m pytest -q
python -m flake8 . --extend-exclude=.venv,venv
```

Веб-тесты используют отдельную временную Django test DB, миграции и
откатываемые транзакции; рабочие SQLite-файлы не изменяются.
Дополнительный pytest-плагин не требуется. Тестовые данные загружаются
из отдельной копии исторической JSON-фикстуры через команду переноса.
SQL-тесты ПР7 сохранены и работают со своими временными SQLite-файлами.
Тесты ПР9 проверяют значения и ID при переносе, повторный запуск,
откат при конфликтах, защиту связей, пагинацию, сортировку,
параметры GET, локальные даты/статусы и статистику с пустыми группами.

Проверено: 159 тестов проходят; `check`, `showmigrations`, проверка отсутствия
новых миграций и flake8 завершаются успешно.

Проект остаётся локальным учебным приложением без разграничения доступа к CRUD.
